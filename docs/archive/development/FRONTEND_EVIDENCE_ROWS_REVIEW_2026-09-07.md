# 请求证据链阅读布局审查

日期：2026-09-07，第十一轮。基于真实页面 `/attribution`、已有 run 与 `req_prefill_0` 审查，不创建展示数据，不发送真实模型问题。

## 问题与取舍

- P1：五列横排把资源和网络的长标识挤到狭窄列；较窄桌面需要横向滚动才能读完。请求、并列资源、网络改为纵向分组，KV Cache、设备执行、集合通信仍在同一并列资源组，不引入三者间的顺序。
- P2：旧模块编号与英文混排成为标题主体。标题使用语义名称，旧编号作为较弱的实现标识保留；原始字段与关联规则不重写。
- P2：每个已绑定节点重复展示实现级关联说明。收进原生“关联规则”展开项；所有非 available 状态的原因仍直接显示，不能通过简化界面隐藏缺口。
- P2：执行与证据记录混用相同图标，长标识在三列中大量换行。改为有明确非因果边界的宽行列表，保留原有三条标识、两条引用预览和完整证据展开计数。
- P2：执行详情使用圆角色块、药丸状态和嵌套单元格。改为分隔线与定义列表，保留请求/解析保真度、来源、回退、差分、检查点等原始数据。

宽行布局增加了默认页面纵向长度，换取完整标识的可读性和窄桌面无需横向浏览。没有用截断或删除证据来压缩页面。更极端数量的源标识与引用仍沿用原有完整展开机制，本轮不改变分页或数据加载策略。
