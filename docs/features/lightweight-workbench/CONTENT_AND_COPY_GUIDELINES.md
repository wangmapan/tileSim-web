# 内容模型与文案规范

## 1. 轻量内容模型

每个任务、概念卡和结果摘要都使用相同的内容骨架：

```text
目标（用户要完成什么）
→ 当前状态（已知/缺失/不可用）
→ 解释（这意味着什么）
→ 证据（来自哪里、什么 revision）
→ 限制（不能推断什么）
→ 下一步（用户可以安全做什么）
```

这套骨架是展示合同，不是新的 report schema；字段值仍来自 canonical output。

## 2. 文案规则

- 先说事实，再说术语：例如“还缺少设备信息（device）”，而不是只显示 `device: unknown`。
- 一个按钮只表达一个动作：`补充信息`、`查看依据`、`进入专业版`、`丢弃草案`。
- 永远明确副作用：`不会创建运行`、`不会调用外部模型`、`草案仅在本页有效`。
- 不使用“智能推荐”“已优化”“预测会达到”等未被证据支持的承诺。
- “可能”“建议”必须说明依据和不确定性；不能用模糊词掩盖 unknown。
- 错误文案包含三部分：发生了什么、影响是什么、下一步是什么。

## 3. 状态词典

| 状态 | 推荐中文 | 禁用替代 |
| --- | --- | --- |
| draft | 草案，尚未创建运行 | 方案已完成、结果 |
| unknown | 未知，当前没有该事实 | 默认、估计 |
| missing | 缺少信息 | 空白、自动补齐 |
| not covered | 当前证据未覆盖 | 不重要、已验证 |
| unsupported schema | 当前版本不支持 | 暂时隐藏 |
| unavailable | 能力暂不可用 | 稍后一定可用 |
| stale | 内容已过期，需要重新确认 | 已自动更新 |
| synthetic | 合成/fixture 证据 | 真实测试 |

## 4. 教学内容边界

概念卡解释“是什么、为什么重要、在 TileSim 哪一步使用”，不写成通用性能结论。示例参数必须带 `example` 标签和“不可直接代表真实结果”说明。任何来自公开资料的说明需在文档或帮助中标注来源，不能让 Agent 生成无来源知识作为事实。

## 5. 国际化与可测试性

中文/英文必须共享状态 ID 和按钮意图，禁止通过字符串比较驱动逻辑。新英文文案写入 `src/i18n/workstreams/`；轻量文案不可扩大共享 legacy catalog。每个状态至少有一个稳定可测试的 accessible name。
