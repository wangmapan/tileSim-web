# Agent 部署方案探索增量开发方案

> 状态：开发计划，基于 2026-11-01 当前工作树。  
> 范围：TileSim Agent 助手与自动探索模块。  
> 约束：保留一次只执行一个实验；不把尚未完成的 Profile、真实 Provider 或生产证据描述为可用能力。

## 1. 背景与目标

当前自动探索已经能在用户授权后，在授权参数范围内串行生成候选、执行实验、读取指标并比较结果。现有探索更接近“固定实验配置下的参数扫描”，还不能完整回答用户通常希望仿真平台回答的问题：

> 在固定模型、固定 GPU 类型和固定卡数的情况下，怎样组织 GPU、选择并行和通信拓扑，才能在不同请求负载下获得更低的端到端延迟；当部署方案固定后，哪些运行参数还能进一步降低延迟或提高有效吞吐量？

本方案把自动探索逐步扩展为“部署方案 + 工作负载场景 + 运行策略”的受约束设计空间搜索，同时解决一个重要交互问题：

> 用户只说“帮我自动探索”，但没有提供足够的固定条件时，助手必须先识别缺口、给出可选建议并请求补充，而不能直接返回原始校验错误，也不能擅自替用户确定模型、卡数或目标指标。

## 2. 当前实现边界

当前已具备：

- 任务识别、页面上下文与权限检查；
- 一次授权后的自动探索；
- LangGraph 阶段控制和 SQLite WAL checkpoint；
- 单 Worker、单实验槽位、每轮只执行一个实验；
- 运行创建、终态等待、验证指标读取、正式取消和状态围栏；
- 候选配置确定性扫描、结果比较和停止条件；
- 运行编号、指标路径、工件摘要和证据引用绑定。

当前正式向 Agent 暴露的参数目录包含：

- 工作负载消息大小倍率；
- 批处理调度策略；
- 最大批处理规模；
- KV Cache 容量；
- 纵向扩展网络带宽和延迟；
- 横向扩展网络带宽和延迟。

当前仍未正式开放给 Agent 自动探索的部署能力包括模型选择、设备选择、张量并行、流水线并行、专家并行、物理 KV 策略和集合通信算法。能力目录中标记为未发布或未闭合的字段不得通过新增提示词、前端隐藏字段或自定义 JSON 强行暴露。

所有本地探索结果继续保持 `local_dev`、`synthetic_trace`、`exploratory`、`not_for_production` 边界；真实 Provider、真实 Profile、生产持久化和生产 verified artifact 需要独立验收。

## 3. 用户目标与交互原则

### 3.1 自动探索不是一个无条件动作

用户输入“帮我自动探索更好的部署方案”时，助手先判断当前上下文是否足以形成可执行实验活动。所需信息分为四类：

1. **固定资源条件**：模型、推理引擎、精度、GPU 类型、GPU 数量、节点边界；
2. **部署候选范围**：允许比较的并行方式、GPU 分组、放置方式和通信拓扑；
3. **工作负载场景**：请求到达率或并发数、输入长度、输出长度、突发模式；
4. **目标与约束**：主要优化指标、延迟上限、错误率上限、资源上限和探索预算。

缺少信息时，助手必须返回“需要补充的信息 + 推荐选项 + 推荐理由”，而不是抛出 `invalid_parameter` 一类内部错误。一次最多询问三个最关键的问题；其余信息可以使用明确标注的建议值，但不能静默写入授权或运行请求。

### 3.2 建议必须可选择、可追踪

助手给出的建议应作为结构化草案展示，例如：

- “如果卡数已固定，建议先比较两种 GPU 分组方案；是否按这两种方案继续？”
- “未提供负载，建议使用低、中、高三个请求场景；是否采用？”
- “未提供目标，建议以端到端延迟 P99 为硬约束、有效输出 token 吞吐量为主要目标；是否采用？”

用户接受建议后，建议值才进入实验草案；用户拒绝或修改建议时，草案应重新校验。助手不得把推荐值伪装成用户输入。

### 3.3 三种结果状态

规划阶段需要明确区分：

- **需要补充信息**：缺少形成实验草案的必要条件；
- **已有建议可继续**：存在默认方案，但需要用户确认；
- **当前能力不支持**：需求需要尚未发布的 Profile 或执行能力，应说明缺口并提供可运行的替代范围。

只有实验草案完整、能力目录确认可执行并且用户完成一次授权后，才进入自动探索执行。

## 4. 目标对象模型

自动探索活动由以下对象组成：

```text
探索活动
├── 固定资源：模型、GPU 类型与数量、引擎、精度、资源预算
├── 部署候选：GPU 分组、并行方式、放置方式、通信拓扑
├── 工作负载场景：请求量、并发、输入/输出长度、突发模式
├── 运行策略：调度、批处理、token 预算、KV Cache、缓存策略
└── 目标约束：主要目标、延迟/错误率/资源约束、停止条件
```

需要把“部署变量”“运行变量”和“场景变量”分开：

- **部署变量**决定资源如何组织和连接；
- **运行变量**决定服务如何调度请求；
- **场景变量**决定在哪些请求条件下评估方案，不应被误写成服务优化参数。

### 4.1 多指标目标

当前探索只有一个指标和一个优化方向，需要扩展为“主要目标 + 硬约束 + 场景聚合”：

```json
{
  "primary_objective": {
    "metric_path": "/summary/output_token_throughput",
    "direction": "maximize"
  },
  "constraints": [
    {"metric_path": "/latency/ttft/p95", "operator": "<=", "threshold": 500},
    {"metric_path": "/latency/end_to_end/p99", "operator": "<=", "threshold": 2000},
    {"metric_path": "/reliability/error_rate", "operator": "=", "threshold": 0}
  ],
  "aggregation": "all_scenarios"
}
```

面向用户的中文解释应使用“主要目标、延迟约束、错误率约束、所有场景均满足”等词，不展示内部字段名。

## 5. 推荐的增量交付顺序

### 阶段一：规划前置与澄清，不改变已有执行语义

目标是让“信息不足”进入可恢复的规划状态。

工作内容：

1. 为 `explore_experiment` 增加规划前置状态，至少包含：收集固定条件、收集负载场景、收集目标约束、展示建议、等待确认；
2. 扩展意图结果，使其能表达缺失信息、建议选项、建议理由和下一步动作；
3. 将当前页面上下文、能力目录和参数目录作为规划输入；
4. 对缺失条件返回中文澄清卡片，不创建探索会话、不占用唯一实验槽位；
5. 用户确认后生成不可变实验草案，草案摘要进入授权绑定；
6. 保留现有任务：方案生成、配置实验、执行仿真、结果解读、报告生成和自动探索。

验收重点：

- 只说“自动探索”时不会直接报参数错误；
- 助手最多询问三个关键问题；
- 建议值必须由用户确认后才能进入草案；
- 缺少运行能力时显示可运行替代方案；
- 未完成规划时不创建运行、不占用实验槽位。

### 阶段二：预定义部署候选比较

目标是在固定资源条件下比较后端已经发布的部署候选，而不是允许模型自由生成拓扑。

工作内容：

1. 新增部署候选的只读 Profile 描述：资源绑定、GPU 分组、并行方式、放置方式、拓扑和可执行状态；
2. 能力目录区分“已发布可执行”“仅描述”“未发布”和“不可比较”；
3. 第一版只允许后端预置的 2–3 个候选进入探索；
4. 每个候选绑定多个工作负载场景；
5. 继续使用单实验槽位，候选和场景按队列串行执行；
6. 每个候选的结果必须绑定候选摘要、场景摘要、运行编号和指标证据。

第一版不开放模型、设备、卡数、并行度和集合通信的任意自由组合；如果真实 lowering 或 Profile 不完整，保持不可执行状态。

### 阶段三：固定部署下运行策略探索

目标是在部署方案不变时调节不增加硬件数量的运行参数。

优先顺序：

1. 批处理调度策略；
2. 最大批处理规模；
3. KV Cache 容量；
4. 后端正式发布后再增加每轮 token 预算、分块预填充、前缀缓存和请求接纳限制。

消息长度、请求量和输入输出长度作为工作负载场景；网络带宽和网络延迟只有在明确表示硬件或拓扑候选时，才进入部署设计空间，不应被包装成无成本运行调参。

### 阶段四：多指标比较与停止策略

目标是从“单指标最大化”升级为满足服务约束的方案选择。

建议指标分组：

- 延迟：首 token 延迟、每 token 延迟、token 间延迟、端到端延迟、P50/P95/P99；
- 吞吐：请求吞吐、输出 token 吞吐、总 token 吞吐、满足服务目标的有效吞吐；
- 资源：排队时间、预填充/解码时间、GPU 利用率、KV Cache 使用率、通信等待；
- 可靠性：成功率、超时率、拒绝率、失败率。

先淘汰违反硬约束的方案，再在剩余方案中按主要目标排名。若多个方案互不支配，返回 Pareto 候选集合和每个方案的取舍，不强行给出唯一最佳方案。

### 阶段五：模型辅助候选建议

第一至四阶段使用预定义候选和确定性扫描。只有能力目录、Profile、运行证据和多指标目标闭合后，才允许模型根据历史结果提出下一候选。模型候选仍必须经过参数授权、Schema、重复候选、预算和后端能力校验，不能直接操作拓扑或运行器。

## 6. 代码与模块落点

### Bridge

- `bridge/contracts/schemas/agent-intent/`：增加澄清、建议和规划结果结构；
- `bridge/contracts/agent_orchestration_capability/`：发布部署候选、场景和运行策略的能力状态；
- `bridge/agent_harness/exploration.py`：增加规划阶段、多指标目标、候选/场景绑定和草案冻结；
- `bridge/services/agent_orchestrator.py`：处理任务识别后的澄清、建议和确认恢复；
- `bridge/services/exploration_service.py`：只在草案确认后创建探索会话和占用槽位；
- `bridge/services/exploration_graph.py`：增加规划恢复路由，保留现有 LangGraph 执行节点；
- `bridge/services/candidate_generator.py`：默认使用预定义候选和确定性扫描；阶段五通过显式注入的模型 Provider 提供受闭世界校验的可插拔候选建议；
- `bridge/services/exploration_worker.py`：继续只负责队列、执行器调用、结果提交和恢复；
- `bridge/services/run_executor.py`：保持统一执行器端口，不让图或 Worker 依赖 TileSim 内部实现；
- `bridge/repositories/explorations.py`：持久化规划草案、建议确认、场景结果、多指标评估和事件。

### 前端协作边界

本轮前端只增加规划状态和中文建议卡片的显示与确认，不把业务规则写入页面组件。页面通过公共 API、TanStack Query 和既有探索 feature 获取状态；未授权、未完成规划和上下文过期时不创建执行副作用。

## 7. 契约建议

新增对象应至少表达：

- 固定资源摘要；
- 部署候选引用；
- 工作负载场景集合；
- 运行策略授权范围；
- 主要目标和约束；
- 建议来源与用户确认记录；
- 能力目录版本、后端身份和上下文版本；
- 预算、停止条件和证据边界。

所有新 Schema 必须：

1. 使用闭世界字段校验；
2. 带 schema identity、contract revision 和 schema-set revision；
3. 生成 TypeScript 客户端和校验器；
4. 运行 `pnpm contracts:generate` 后提交生成结果；
5. 不新增未被能力目录确认的 `agent_exposed` 字段；
6. 让历史探索请求保持兼容，或明确拒绝并给出用户可读的迁移建议。

## 8. 测试与验收矩阵

### 规划交互

- 未提供固定资源时进入澄清，不返回原始 Schema 错误；
- 已有部分上下文时只询问缺失信息；
- 建议值必须确认后冻结；
- 用户修改建议后重新计算草案摘要；
- 未确认草案不创建运行、不占槽位。

### 能力边界

- 未发布 Profile 不出现在可执行候选中；
- 模型、设备、并行度等未开放字段不能通过请求注入；
- 自定义 JSON 被 Schema 接受不等于自动获得执行能力；
- 工作负载场景不能被误当成运行调参。

### 执行与恢复

- 候选与场景组合按单实验串行执行；
- 进程重启不会重复创建已确认运行；
- 未知结果进入恢复状态并保留槽位；
- 确认取消后释放槽位；
- 迟到结果不能覆盖已取消运行；
- 结果、配置、候选、场景和证据绑定一致。

### 多指标决策

- 违反硬约束的方案不会被选为最佳；
- 没有唯一支配方案时返回 Pareto 候选；
- 缺少某个必需指标时不能伪造比较结果；
- 停止原因能区分预算耗尽、无改进、约束不可满足和需要人工处理。

## 10. 完成定义

阶段一完成后，用户只说“帮我自动探索”时，助手能够：

1. 读取当前上下文和能力目录；
2. 找出缺失的固定条件、负载和目标；
3. 用中文提出不超过三个关键问题；
4. 给出可选择的默认建议及理由；
5. 在用户确认后生成结构化实验草案；
6. 只有草案通过能力和参数校验、用户完成一次授权后才启动探索。

后续阶段完成后，系统才能在固定资源约束下比较部署候选，并在固定部署下探索运行策略，最终按多指标约束选择方案。

## 11. 阶段二至四实现记录（2026-11-01 当前工作树）

阶段二至四已接入现有执行边界。确定性候选生成器现在以 Bridge 能力目录中已发布且可执行的部署候选为外层维度，再组合已确认的运行策略和授权参数；模型请求体中的候选列表仍不会成为权威来源。候选记录保存部署候选摘要、资源绑定、策略摘要、候选组合键和独立候选幂等键。场景选择在候选内部逐个进行，运行幂等键包含候选幂等键和完整场景摘要 digest，因此同一候选的不同场景不会复用运行编号，不同候选也不会复用运行编号。

运行策略在确认草案、授权摘要、候选记录和正式 `run_request` 执行信封之间冻结。当前只允许能力目录已经发布并有执行闭环的批处理调度、最大批处理规模、KV Cache 容量和消息大小倍率；模型、设备、GPU 数量、张量/流水线/专家并行、物理 KV 策略和集合通信算法仍不能由 Agent 自由注入。正式请求继续保留完整基线模板，只覆盖本候选实际改变且已授权的字段；请求摘要、候选摘要、场景摘要、策略摘要和草案摘要进入执行副作用账本。

候选完成全部场景后才进行多指标评估。缺少必需指标或证据的候选被标记为不合格；违反硬约束的候选保留审计记录但不会成为最佳方案。完成所有候选后，报告区分合格候选、约束失败候选、Pareto 候选、推荐候选和停止原因；多个互不支配候选时不强行选择唯一推荐。每个场景结果保留运行编号、指标路径和证据引用。LangGraph、单 Worker、单实验槽位、未知结果恢复、暂停/恢复、确认取消释放槽位及迟到结果 fence 均保持不变。

阶段五的模型辅助候选边界已实现，并已接入正式 `AssistantModelCandidateProvider` 适配器。`ModelCandidateGenerator` 默认仍不调用模型；只有 `TILESIM_EXPLORATION_MODEL_CANDIDATES=on`（或兼容别名）时，Bridge 才通过现有 AssistantModel 配置、认证、超时和结构化 JSON transport 请求候选。模型上下文绑定固定资源、已发布可执行候选、授权参数、运行策略、所有已执行候选及其场景指标/证据/约束判定、当前最佳、Pareto 和剩余预算；提案只允许闭世界 Schema 中的授权 JSON Pointer 变化与已发布候选编号。Schema、能力目录、授权、固定部署/场景、规范化摘要、重复候选和轮次/模型/工具/运行预算校验都在执行队列前完成，非法或不可用模型优先回退确定性生成器，无回退候选进入 `manual_intervention_required/candidate_generation_failed`。模型节点保留 LangGraph checkpoint、单 Worker/单槽位/串行执行、暂停恢复、取消和未知结果恢复语义。模型不能生成模型名、设备或 GPU 拓扑、并行方式、物理 KV、集合通信、未发布 Profile、Shell、路径、URL 或工具调用。新增 controlled Provider acceptance 与隔离 synthetic smoke 只验证本地适配器和边界；真实外部 Provider、Profile 和生产 verified artifact 尚未完成，不能把本地 synthetic 结果升级为真实执行或生产验收。
